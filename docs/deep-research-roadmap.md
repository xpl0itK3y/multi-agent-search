# Deep Research Roadmap

Превращение **Multi-Agent Search & Optimizer** в систему уровня «Gemini Deep Research» — с прицелом обойти его по проверяемости и прозрачности.

> Статус документа: черновик v1. Это план, а не финальная спецификация — раздел «Открытые решения» в конце требует ответов перед стартом P0.

---

## 1. Видение и принцип «лучше Gemini»

Мы не догоняем Gemini по широте охвата веба. Мы выигрываем на трёх осях, где у нас **уже есть фундамент**, а у Gemini — слабые места:

1. **Verifiable** — каждое утверждение привязано к источникам, с аудитом цитат и оценкой уверенности (база: `ClaimVerifierAgent`, аудит цитат в `AnalyzerAgent`).
2. **Conflict-aware** — система **подсвечивает** разногласия источников, а не сглаживает их в гладкий текст (база: `_detect_conflicts`, секция «Конфликты»).
3. **Transparent & controllable** — грейды качества источников, явный бюджет (токены/время/источники), возобновляемость после сбоя (база: `SourceCriticAgent`, чекпойнты графа), **+ видимый процесс рассуждения** (raw reasoning от R1 + narrative trace, как extended thinking у Claude) — Gemini это прячет. См. frontend-roadmap §4.1.

Позиционирование одной строкой: **«verifiable, conflict-aware deep research, self-hosted и дёшево»**.

### Что значит «deep research» технически

Сдвиг парадигмы: от **одноразовой декомпозиции** (`orchestrator.run_decompose` → поиск → один отчёт) к **итеративному агентному циклу** «planner → researcher → gap-analysis → (до-поиск) → writer → verifier» с обратной связью и бюджетом.

## 3. Целевая архитектура

### 3.1 Схема агентов (целевой цикл)

```
                 ┌─────────────────────────────────────────────┐
                 │             ClarifierAgent (new)             │
   user query ──▶│  задаёт 1–3 уточнения (опционально)          │
                 └───────────────────┬─────────────────────────┘
                                     ▼
                 ┌─────────────────────────────────────────────┐
                 │          PlannerAgent (reasoning)            │  ← orchestrator++
                 │  план = список sub-questions + статусы       │
                 │  ▶ показывается юзеру на правку/подтверждение │
                 └───────────────────┬─────────────────────────┘
                                     ▼
        ┌────────────────── ИТЕРАТИВНЫЙ ЦИКЛ (budget-bound) ──────────────────┐
        │                            ▼                                        │
        │   ┌──────────────────────────────────────────────┐                 │
        │   │   ResearcherAgent  (параллельно по sub-Q)     │                 │
        │   │   search → extract → summarize-to-NOTES       │                 │
        │   └───────────────────┬──────────────────────────┘                 │
        │                       ▼                                             │
        │   ┌──────────────────────────────────────────────┐                 │
        │   │   NotesStore (pgvector) — дедуп, retrieval     │                 │
        │   └───────────────────┬──────────────────────────┘                 │
        │                       ▼                                             │
        │   ┌──────────────────────────────────────────────┐   gaps remain   │
        │   │   GapAnalyst (reasoning)  ← replan++           │──── & budget ───┘
        │   │   «достаточно? какие под-вопросы открыты?»     │      left
        │   └───────────────────┬──────────────────────────┘
        │                       │ done / budget exhausted
        └───────────────────────┼─────────────────────────────────────────────
                                ▼
                 ┌─────────────────────────────────────────────┐
                 │     WriterAgent (analyzer++)                 │
                 │     outline → секции → сшивка                │
                 └───────────────────┬─────────────────────────┘
                                     ▼
                 ┌─────────────────────────────────────────────┐
                 │  VerifierAgent (source_critic+claim_verifier)│
                 │  аудит цитат, конфликты, покрытие, confidence│
                 └───────────────────┬─────────────────────────┘
                                     ▼
                              финальный отчёт + webhook/экспорт
```

### 3.2 Модель состояния (research scratchpad)

Расширяем `graph_state` (уже персистится в `researches.graph_state`) до полноценного состояния агента:

```jsonc
{
  "plan": [
    {"id": "q1", "question": "...", "status": "open|researching|done", "priority": 1}
  ],
  "notes": [          // конспекты, не сырой контент
    {"id": "n1", "sub_question_id": "q1", "claim": "...",
     "source_id": "S3", "confidence": "high", "embedding_id": "..."}
  ],
  "iteration": 2,
  "budget": {                       // бюджет-менеджер
    "max_iterations": 4, "max_sources": 60, "max_tokens": 400000,
    "max_wall_seconds": 900,
    "spent_sources": 31, "spent_tokens": 142000, "started_at": "..."
  },
  "open_gaps": ["q4 has no primary source"],
  "decisions": [      // нарративная трасса для UI
    {"step": "gap_analysis", "narrative": "Покрыто 3/5 под-вопросов, до-ищу q4 и q5"}
  ]
}
```

Принцип: **researcher конспектирует источники в `notes` (claim + source_id + confidence)**, а не таскает сырой контент по итерациям. Это сдерживает рост контекста (map-reduce) и даёт writer'у чистый материал.

## 4. Дорожная карта по фазам

Каждая фаза самостоятельно ценна и поставляема. Порядок = по соотношению эффект/риск.

### P0 — Оживить цикл + каркас управления (фундамент)

**Цель:** включить итеративное углубление как управляемый, безопасный по бюджету цикл. Без новых внешних зависимостей.

| Изменение | Файлы | Тип |
|---|---|---|
| Развыключить ветвление графа (сделать лимиты конфигурируемыми, дефолты > 0 для нового режима) | `src/config.py`, `src/graph/research_graph.py` | M |
| Бюджет-менеджер: лимиты итераций/источников/токенов/времени + авто-стоп | новый `src/graph/budget.py`, `deepseek.py` (лимиты поверх учёта) | M |
| Гибридная маршрутизация моделей: `planner_model` / `writer_model` / `repair_model` (+ проброс `reasoning_content` от reasoning-модели наружу для UI) | `src/config.py`, `src/providers/deepseek.py`, bootstrap | M |
| Детектор «прогресс не растёт» (стоп при отсутствии новых уникальных источников) | `src/graph/research_graph.py` | S |
| Перевести gap-анализ (`ReplanAgent._llm_queries`) на reasoning-модель | `src/agents/replan.py` | S |

**Миграции БД:** нет (используем существующий `graph_state`).
**Риски:** рост стоимости/латентности — митигируется бюджет-менеджером; зацикливание — митигируется hard-стопами.
**Критерий готовности:** на наборе из 10 запросов HARD-режим делает 2–4 итерации, всегда останавливается по бюджету, средняя стоимость ≤ целевой (см. §6).

**Критерий готовности:** пользователь может отредактировать план до запуска; уточнения поднимают релевантность на eval-наборе (§8).

### P2 — Глубокий поиск + конспекты + retrieval

**Цель:** снять потолок по широте охвата; убрать рейт-лимиты DDG.

| Изменение | Файлы | Тип |
|---|---|---|
| Абстракция `SearchBackend` + провайдеры Tavily/Exa рядом с DDG (фолбэк-цепочка) | рефактор `src/providers/search.py` | M |
| Кэш результатов поиска и извлечений (Postgres-таблица + TTL) | новый репозиторий, alembic | M |
| `NotesStore` на **pgvector**: эмбеддинги конспектов, семантический дедуп, retrieval по под-вопросу | новый `src/repositories/notes_store.py`, alembic (pgvector ext) | L |
| Researcher конспектирует источник → notes (дешёвая модель), а не таскает сырьё | `src/agents/search.py` / новый researcher | M |
| Поднять конкурентность извлечения и лимиты источников для deep-режима | `src/config.py`, `search_depth_profiles.py` | S |

**Миграции БД:** `CREATE EXTENSION vector`; таблицы `search_cache`, `research_notes(embedding vector)`.
**Внешние зависимости:** `tavily-python` или `exa-py`; ключ API; `pgvector`.
**Риски:** стоимость платного поиска — митигируется кэшем + бюджетом; качество эмбеддингов.
**Критерий готовности:** медиана 40–100 уникальных источников на HARD-отчёт без бана; дубликаты конспектов < 10%.

**Цель:** стабильно длинные структурные отчёты + прозрачность процесса.

## 5. Поток данных: было → стало

**Было:** `POST /research` → (bg) decompose → N search-jobs → все done → 1 finalize-job → 1 отчёт.

**Стало:**
```
POST /research → CLARIFYING → (clarify) → PLANNING → AWAITING_APPROVAL
   → (approve) → RESEARCHING ┐
                             ├─◀ iterate (researcher ∥ → notes → gap-analysis) ─┐
                             └────────────────── budget left & gaps ────────────┘
   → WRITING → VERIFYING → COMPLETED → webhook/экспорт
```
Чекпойнты графа сохраняются на каждом переходе (механизм `checkpoint_graph_state` уже есть) → возобновляемость остаётся.

## 6. Бюджет, стоимость и латентность

Прикидка на **medium** (3 итерации × 5 под-вопросов × ~8 источников ≈ 120 чтений):

| Статья | Токены (вход / выход) | Модель |
|---|---|---|
| Конспекты источников (120 × ~1.5k/0.4k) | 180k / 48k | дешёвая (chat) |
| Планирование + gap-анализ (4 вызова) | 32k / 4k | reasoning |
| Outline + секции + сшивка | 30k / 12k | chat/reasoning |
| **Итого** | **~242k / ~64k** | |

**Стоимость (DeepSeek: $0.14/M вход, $1.10/M выход):** ≈ **$0.10 за medium-отчёт**, HARD ≈ $0.3–0.5. Это на порядок дешевле сопоставимых проприетарных систем — **прямой аргумент для self-hosted**. Платный поиск (Tavily ~$0.005–0.01/запрос) добавит центы при кэшировании.

**Латентность:** medium ≈ 3–8 мин, HARD ≈ 8–20 мин (доминируют последовательные итерации). Параллелизм researcher'ов по под-вопросам — главный рычаг сокращения.

**Бюджет-менеджер (P0) должен жёстко ограничивать:** `max_iterations`, `max_sources`, `max_tokens`, `max_wall_seconds` — с авто-стопом и понятным сообщением «остановлено по бюджету».

## 7. Выбор моделей и поисковых провайдеров

**Модели (гибрид):** базовая — **`deepseek-v4-pro`** (`deepseek_model`), **выбирается пользователем** из каталога `src/model_catalog.py` (V4 Pro / V4 Flash, frontend §4.4) и валидируется на сервере.
- *Writer / Researcher-конспекты* → `deepseek-v4-pro` (для массовых конспектов можно дешевле — `deepseek-v4-flash`, настраивается).
- *Planner / GapAnalyst* → reasoning-вариант (`deepseek_reasoner_model`), который **отдаёт `reasoning_content` отдельно** от ответа — «сырой ход мысли» стримится в UI как headline-фича (frontend §4.1). **Нужно проверить по DeepSeek-доке/дашборду**, есть ли у `v4-pro` thinking-режим/`reasoning_content`; если нет — указать отдельную reasoner-модель (`DEEPSEEK_REASONER_MODEL`). Из текущего окружения API недоступен (нет внешней сети), проверить вручную.
- *Repair* → `deepseek_repair_model` (как сейчас).
- Провайдер читает `reasoning_content`, если он есть, и **мягко деградирует** (просто без блока «Размышления»), если модель его не возвращает.

Реализация: расширить `DeepSeekProvider`/bootstrap до выбора модели по роли (минимальный рефактор, провайдер уже параметризован моделью).

**Поиск (фолбэк-цепочка):**
| Провайдер | Плюсы | Минусы |
|---|---|---|
| **Tavily** | заточен под AI-ресёрч, отдаёт чистый контент | платный |
| **Exa** | семантический/neural поиск, find-similar | платный |
| Brave / SerpAPI | широкий веб | платный, сырой HTML |
| DuckDuckGo (есть) | бесплатно | рейт-лимиты, мелко |

Рекомендация: Tavily как основной для deep-режима + DDG как бесплатный фолбэк; абстракция `SearchBackend` чтобы менять без боли.

## 8. Как мерить «лучше» (eval-харнесс)

Без измерений «лучше Gemini» — лозунг. Завести лёгкий eval **до P0**:

- **Золотой набор** из 15–25 запросов (tech, новости, сравнения, ru/en/es).
- **Метрики на отчёт:** покрытие плана (% под-вопросов с ≥1 источником), доля утверждений с цитатами, доля primary-источников, число вскрытых конфликтов, fail-rate, токены/стоимость, latency.
- **Citation faithfulness:** доля цитат, где токены строки реально пересекаются с источником (логика уже есть в `_unsupported_citation_lines`).
- **A/B:** старый одноразовый пайплайн vs новый цикл на одном наборе.
- (Опц.) LLM-as-judge сравнение с публичным выводом Gemini Deep Research по тем же запросам.

Прогонять как `pytest -m eval` или отдельный скрипт в `scripts/`.
